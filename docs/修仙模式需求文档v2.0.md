## 1. 产品定位与愿景

将 WorkBuddy 的每一次使用变为一场"修行"：

- **提问 = 历练**，**回答/完成任务 = 悟道**，**使用 Skill = 修习功法**，**完成复杂多轮任务 = 闭关突破**。
- 系统自动记录行为、累计"修为值"，沿境界阶梯晋升，把工具使用变成有养成感的长期修行。
- 通过 **灵力石（资源）→ 天赋树（养成）→ 论道 PK（对抗）→ 防篡改核算（信任）** 四层递进，从单机养成升级为有周期刺激与互动的玩法。

**设计原则**
- **全程零交互自主运行**：升级、突破、掉落、解锁均按规则静默执行，不打断对话。
- **正向体验**：不掉分、只做温和提醒。
- **真实可对比**：PK 接入共享榜真实数据，非纯虚拟对手。

## 2. 核心循环

```
用户使用 WorkBuddy（提问 / 完成任务 / 调用 Skill）
        │
        ▼
行为采集 → 修为计分 → 功法熟练度累计 → 灵力石/随机奖励判定
        │
        ▼
突破阈值? ──否──► 继续修行
        │是
        ▼
境界晋升（自动写入修炼日志 + 小结播报）
        │
        ▼
同步论道榜主表（upsert，有则更新无则新增）
```

每圈产出"修为"，积累到阈值触发突破；主表同步使修行可被他人看见与对比。

## 5. 修为计分模型

### 5.1 维度

| 维度 | 来源 | 说明 |
|------|------|------|
| 提问（历练） | 用户提问 | 按质量分档 |
| 回答（悟道） | 任务完成 | 基础分 + 实体产出加成 |
| 使用 Skill（功法） | 调用 Skill | 加分 + 功法熟练度 |
| 持续修行（道心） | 连续活跃 | 连续天数递增奖励 |
| 突破加成（闭关） | 跨多轮大任务 | 完成一次性突破级修为 |

### 5.2 评分初值（已定稿，1 周校准微调）

- 提问：普通单轮 +5；复杂多轮（≥3 轮或含文件产出/Skill 调用）+15；复杂且调 Skill +25。
- 完成：基础 +10；每实体文件 +20（封顶 3 个，+60）；跨轮闭关 +100。
- Skill：每次 +10 修为，对应功法熟练度 +1（封顶 10）。
- 道心：连续第 N 天首任务 +N×2（封顶 7 天，单日 +14），断更归零。
- 灵力石：夜间（20:00–24:00）或节假日每次会话掉 1–3；法定节假日额外 +5。

**取值信号（零交互判定）**：任务轮数 + 是否有文件产出 + 是否调用 Skill → 分档。基础分低、产出/Skill 加成高，引导"用工具出成果"。

> ⚠️ 随机奖励每日触发上限 **3 次/日**（见 §9）。

## 6. 功法体系（Skill 自动分配）

### 6.1 自动分配（零交互，规则驱动）

首次调用某 Skill 即按 `config/skills_map.json` 归类入图鉴并累计熟练度。

| 功法系别 | 对应 Skill 类型 | 解锁境界 |
|---------|---------------|---------|
| 符箓系 | 文档/写作/润色（tencent-docx、humanizer 等） | 初始 |
| 阵盘系 | 表格/数据/报表（sheet、excel 类） | 筑基 |
| 炼器系 | 图像/视频/3D（ImageGen、VideoGen、3D 等） | 元婴 |
| 傀儡系 | 浏览器/自动化（agent-browser 等） | 元婴 |
| 望气系 | 搜索/研究/抓取（WebSearch、WebFetch 等） | 金丹 |
| 传音系 | 邮件/通讯类 | 金丹 |
| 杂学系 | 其余未匹配 | 初始 |

### 6.2 熟练度与加成

- 熟练度 1～10，由使用次数与完成质量驱动。
- 熟练度越高，该功法修炼（获取修为）时获得倍率加成（二期落地倍率）。

## 9. 随机奖励（带条件限制）

在自动升级之上叠加"天降机缘"，**必须命中条件才触发**，避免无脑发放。

| 奖励类型 | 内容 | 获得条件 |
|---------|------|---------|
| 灵力石 | 额外掉落 | 连续活跃 ≥ 3 天 |
| 天赋点 | 解锁加成 | 当日完成复杂任务 ≥ 2 |
| 天材地宝 | 一次性增益 | 夜间/节假日时段 |
| 功法残卷 | 加速某功法熟练 | 首次修炼某新功法 |
| 顿悟 | 修为暴击 | 突破境界当日 |

约束：每日触发上限 **3 次/日**（防刷）；随机抽取按权重分配；全部静默入账，仅在修炼小结列出。

## 10. 论道 PK + 双表 + 防篡改

### 10.1 解锁与匹配

- 解锁：练气 **2 级**（小阶第 2 层）开放论道；此前提示"道行尚浅，练气二层方可论道"。
- 同级别匹配：仅从主表抽**同大境界**真实对手；无同境对手则降级 `±1` 境或引导本地演武。

### 10.2 对手与结算

- 对手来源：论道榜共享表真实修士，随机抽选取其修为/境界/主修功法。
- 结算：双方属性差 + 功法克制 + 随机波动 → 胜负与奖惩（掠取灵力石/修为）。
- 文字可视化：回合制战报（文字/表格卡片），纯文本。

### 10.3 功法克制（五行循环，已定稿）

傀儡克望气 → 望气克炼器 → 炼器克阵盘 → 阵盘克符箓 → 符箓克傀儡；传音/杂学中立。

### 10.4 总修仙分值（PK 排序依据，确定式可重算）

```
T = 修为 W
  + 灵力石 L × 0.5
  + 功法熟练度和 S × 10
  + 胜场 Wn × 20 − 负场 Ln × 5
  + 连续活跃天数 D × 3
```
（S 上限 S_max=70 = 7×10；D 上限 D_max=30 天 ≈ +90。以 min(·,max) 截断。）

> ⚠️ **合理性提示**：修为 W 已含"道心"对连续活跃的加成，本式再计 D×3 会双重加权连续活跃。若试运行发现"签到主导排名"，建议二选一（保留 W 道心 / 移除本式 D×3）。当前保留以与已定稿系数一致。

### 10.5 防伪造设计（已定稿：无后端 · 日志可溯 / 路线②）

采用「**行为日志为唯一真相源 + 日志链校验**」方案，不依赖任何后端即可让伪造**可检测、可追溯、不可抵赖**。校验码仅作廉价粗筛，权威校验改为日志重放。

**① 行为日志（本地唯一真相源）**
所有计分动作以追加方式写入 `~/.workbuddy/xiuxian/history.jsonl`，单条：
`{"ts":<UTC>, "type":question|task|skill|daily|reward|pk_win|pk_loss, "meta":{}, "dxp":<int>, "dlingshi":<int>, "realm_from":, "realm_to":}`
`state.json` 的修为/灵力石/战绩等**全部由重放该日志得出**，日志即权威，state 只是缓存视图。

**② 日志链签名（廉价完整性层）**
```
LOG_HASH  = SHA256( 各行哈希拼接 )                  # 跨用户"日志承诺"，供 PK 挑战验证
字段串    = 道号|修为|灵力石|战绩|总修仙分值|最近活跃|更新时间
校验码    = SHA256( SALT + 字段串 ).hexdigest()[:16]  # 仅粗筛"字段是否被懒人改"
```

**③ 跨用户日志承诺（支撑 PK 挑战）**
每次同步，除 upsert 主表外，另将 `LOG_HASH + 校验码 + 最近日志时间戳`写入主表（或战报表"承诺"子表）。挑战方据此验证对方声明值是否由一份一致的日志支撑，无需实时拉取全文。

### 10.6 每次 PK 强制三层复核（日志可溯）

对**自身 + 每个同境候选对手**：
1. **公式核算**：重算 `T'`，与表内总修仙分值不符 → 标"数据异常"。
2. **签名核算**：重算 `H'`，与表内校验码不符 → 标"签名不符"。
3. **日志重放核算（权威）**：取对方 `LOG_HASH` 承诺，挑战方用**与 `common.py` 完全一致的计分规则**在本地重放对方日志，得出 `修为'/灵力石'/战绩'`；与对方声明值偏差超容差（取整容差 ±1）→ 标"道行存疑"。
4. 任一不过 → 不进匹配池，战报注"道行存疑"；可在战报表写"质疑"标记供公开查看。
通过三层者进入随机抽选与回合制对战。

> 设计要点：单人改 `state.json` 不配套改日志，重放即暴露；伪造一份"规则一致、时间戳合理"的完整日志成本极高，且任意单点不一致在挑战重放中被抓。这是路线②"可检测、不可抵赖"的核心。

### 10.7 双表结构与结算权威性

- **主表只存本人行**：每实例仅 upsert 自己道号行；读他人行仅用于匹配（只读）。
- **战报表存对战结果（只追加）**：A 胜 B → A 向战报表追加 `{挑战者,守方,结果,战前修为快照,掠取灵力石,签名,状态=pending,时间戳}`。
- **败方异步兑现**：B 下次运行时扫 `守方=B 且 pending` 记录，校验挑战者签名与战前快照合理性后，在**本地**扣减并 upsert 主表，标记 resolved。
- **效果**：A 无法静默改写 B 行；B 行永远由 B 自己按本地日志改写。
- **日志即真相源**：B 的主表行由 B 用本地日志重放后 upsert；A 既改不了 B 行，也伪造不出 B 的合法日志（伪造日志须满足规则一致性与时间戳序列，单次不一致即在 §10.6 重放中暴露）。

> ⚠️ 残余风险（SALT 公开）：恶意 A 仍可伪造指向 B 的战报诱 B 自罚。路线② 软性防护：① 仅当挑战者签名有效且战前修为 ≥ 守方才兑现；② 单挑战者每日写入限流；③ B 侧默认"待确认"而非直接扣减；④ 战报须附带挑战者 `LOG_HASH`，B 兑现前先重放校验其真实性。彻底防御（密码学级不可伪造）需受信任后端，列为三期。

### 10.8 主表权限与自愈

- 当前"所有人可编辑"以支撑各实例自动 upsert；叠加：① 每日 UTC 0:00 快照；② 校验码检测（失配行标"可疑"跳过入池）；③ 破坏自愈（表清空/行数骤降时从最近快照恢复）。
- 细粒度"只读 + 受控写入"受腾讯文档权限模型限制，列为二期。

## 11. 数据存储与触发

### 11.1 触发机制

- 采用**自动化驱动的周期性对账**：recurring Automation 按 rrule 每日固定时刻（建议 09:00、21:00 两次）触发本 skill 执行对账；用户亦可随时手动 `/xiuxian 结算` 即时结算。
- **平台约束**：Automation 仅支持 recurring/once，**不支持"每次新会话开启"事件**；故"实时逐会话计分"改为「定时对账 + 手动命令」双入口。
- 运行时读本地会话记录，依 `state.last_cursor`（上次处理到的轮次时间戳）识别新增轮次，分类套 §5 计分累加，更新境界/突破/灵力石/随机奖励，最后 upsert 主表。

### 11.2 存储格式

- 权威数据源：`~/.workbuddy/xiuxian/state.json`（用户级，跨项目持久）。记录：道号、境界、小阶、修为、灵力石、功法熟练度表、连续活跃、last_cursor、device_id、修炼历史。
- 主表仅作对外同步镜像。

### 11.3 多设备策略

- 道号绑定 `device_id`（首次运行生成）。主设备负责 upsert。
- 同号其它设备为**次级设备**，默认**只读观光**（可看榜、可参与匹配，不回写统计），避免 last-write-wins 丢进度。
- 可切换主设备：先拉取主表行合并最大值后再接管。

## 15. 技术接口契约（实现者必读）

### 15.1 state.json Schema
```json
{
  "daohao": "青云子",
  "realm": "练气", "sub": 2,
  "xiuwei": 95, "lingshi": 8,
  "skills": {"符箓":3,"阵盘":1,"炼器":0,"傀儡":0,"望气":2,"传音":0,"杂学":4},
  "streak": 4, "last_cursor": "2026-08-25T08:00:00",
  "device_id": "dev_abc123",
  "unlocked_talents": ["talent_root"],
  "pk": {"win":3,"lose":1,"loot":6},
  "history": []
}
```

### 15.2 脚本 I/O 约定
- `reconcile.py`：输入=会话日志 + state.json；输出=更新后的 state.json + history.jsonl 追加。
- `sync_leaderboard.py`：读 state.json → 重算 T 与校验码 → upsert 主表（道号键）；读主表做候选对手校验；每日 0:00 写快照。
- `pk_engine.py`：输入=state + 主表同境候选；输出=文字战报（str）+ 战报表追加记录 + 本地灵力石/修为变动（胜方即时、败方异步）。
- `render_dongfu.py`：输入=state + 主表排名快照；输出=`~/.workbuddy/xiuxian/dongfu.html`。

### 15.3 腾讯文档读写约定
- upsert：以「道号」为唯一键，命中更新、未命中追加。
- 校验码算法严格按 §10.5，SALT 取自 config。
- 战报表只追加，记录状态机：pending → resolved。
- 失败重试 + 快照自愈，不阻塞本地逻辑。

### 15.4 关键常量（写 config）
- SALT、`S_max=70`、`D_max=30`、PK 解锁=练气2级、随机奖励日上限=3、评分初值（§5.2）。

### 16.2 已知局限（诚实声明）
1. **SALT 随代码分发（已缓解）**：原"绝对防伪需后端"仍为事实；但已定稿路线②（行为日志为真相源 + 重放挑战），使伪造**可检测、可追溯、不可抵赖**，对休闲玩法足够。密码学级不可伪造仍列为三期（受信任后端）。
2. **PK 对手生态依赖**：异步真实对手需足够多的人安装并同步主表；冷启动期建议同时提供"本地演武"保底。
3. **实时性**：计分靠定时对账/手动命令，非逐轮实时（平台 Automation 限制）。
4. **主表权限**：全员可编辑有被破坏风险，靠快照+自愈缓解，非根治。
5. **节假日表**：静态，需年度更新或加联网校准开关。
6. **公式双重加权**：连续活跃在 W(道心) 与 T(D×3) 中重复计，上线后观察并二选一。

### 16.3 建议落地顺序
1. 一期：state 模型 + reconcile + sync + pk_engine + render_dongfu + 斜杠命令 + 两张表联动。
2. 一期验收后跑 1 周真实样本，调阈值/系数（±20%）。
3. 二期：天赋消费、倍率、日报、本地演武、论道榜视图、法宝、门派、洞府增强。
4. 三期（如需）：评估自建后端以支持实时对战与绝对防伪。

### 16.4 风险等级
- **P0（已闭环）**：计分触发机制（定时+手动）、PK 结算权威性（双表+异步兑现）。
- **P1（已决策）**：阈值/系数定稿、主表破坏缓解、五行克制定稿、多设备策略。
- **P2（持续优化）**：节假日表维护、公式双重加权、战报自罚软防护、同境无对手兜底。
